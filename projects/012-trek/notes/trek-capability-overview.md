# TREK 研究总览：能力、原理、探索与价值

整理日期：2026-09-22。研究基准为本地运行的 TREK 4.3.0，固定提交 `b98787f83698f3beee1b9a8475121c52f0caf07c`，上游许可证 AGPL-3.0。

**当前决定：按用户要求暂停继续实现产品，保存能力、成果、问题和可选方向。本文件中的扩展目标不代表已交付，也不代表已经决定继续开发。**

[查看完整研究总览图](../assets/trek-research-overview-2026-09-22.png) · [上游仓库](https://github.com/liketrek/TREK) · [项目入口](../README.md)

## 先看三个判断

1. **TREK 是可自行部署的旅行管理应用。** 用户称它为“库”，但它实际提供完整前后端与旅行业务，而不是只供调用的地图组件库。
2. **最值得复用的是地点、每日安排、路线衔接与保存能力。** 地图、地点搜索、道路和外部导航由不同服务共同提供，TREK 将它们接入旅行管理流程。
3. **对我们的机会，是做可信的视觉城市导览。** 让首次到访的人看图认识片区，选择景点和餐厅，了解条件，并进入真实地图和到达指引。这个方向需要在 TREK 基础之外补内容、生成与信息维护能力。

## 1. TREK 原生能力：哪些是上游提供的

下表根据固定版本 README、wiki 和源码整理。**上游有此能力，不表示我们已逐项实测或本机已启用全部模块。**

| 能力组 | 主要内容 | 对使用者的作用与前提 |
| --- | --- | --- |
| 地点搜索与探索 | 名称搜索、分类探索、地图选点、地点详情、照片、收藏集合 | 找到地点并纳入旅行；搜索结果质量由数据覆盖与服务配置共同决定 |
| 地图呈现 | 点位、行程、路线、底图和显示设置 | 把地点放在空间中理解；底图和部分增强功能依赖外部地图服务 |
| 行程安排 | 旅行、日期、每日地点、停留与备注、住宿和交通安排、拖拽调整 | 将零散目的地变为可执行的日程 |
| 路线辅助 | 地点顺序优化、道路路线、距离和预计时长、外部地图打开 | 帮助排顺序和判断通勤；不等于实时交通下的全局最优导航 |
| 预订与文件 | 住宿、航班、火车、车辆等资料，预订附件和文件管理 | 集中已有出行资料；保存记录不等于购买、订位或预约成功 |
| 文件导入 | KDE Itinerary / KItinerary 解析；可配置 AI 辅助识别 | 从文件提取候选信息；本机未安装 KItinerary，可选 AI 导入未实测 |
| 费用与分账 | 预算、支出、币种、付款人、分摊、余额和结算建议 | 降低多人记账与对账成本；汇率等可能依赖外部数据 |
| 清单与准备 | 行李清单、模板、负责人、待办任务 | 旅行前准备与分工 |
| 多人协作 | 成员与角色、共享旅行、实时变更；聊天、笔记、投票等扩展模块 | 共同维护同一旅行；模块和权限需按实际配置启用 |
| 分享与输出 | 共享入口，PDF、GPX、ICS、CSV 等不同用途导出 | 分享计划、对接地图与日历或后续整理；本轮未完整实测各类导出 |
| 日记与足迹 | 旅行日记、到访记录、Atlas / 足迹统计等 | 留存旅行经历；原生 Atlas 的足迹含义与我们研究的城市生成插画不同 |
| 日常辅助 | 天气、日历订阅、通知、仪表盘等 | 补充出行上下文；覆盖、有效期和可用性由相应服务决定 |
| 离线体验 | PWA 资源缓存、本地存储和部分离线编辑、重连同步 | 降低网络不稳定影响；不是全部外部服务可离线使用，编辑对象和冲突处理有范围 |
| 开放与扩展 | 插件、公共 API、MCP 工具与资源、管理配置 | 供定制前台和外部 AI 在授权范围内接入旅行业务 |
| 自托管与管理 | 本地／服务器部署、用户与权限、存储、备份及相关设置 | 掌握自己的部署与数据，同时承担运行、升级和维护工作 |

## 2. 底层实现：旅行系统如何连接地图

### 业务与存储

`React / TypeScript / Vite / Zustand 界面 → NestJS 业务接口 → SQLite 数据持久化`

界面负责交互和选择状态；服务端负责旅行、地点、每日安排、成员权限等规则；数据保存到服务端。WebSocket 将旅行变更同步给客户端。协作采用服务端状态和相应覆盖规则，不能直接称为 CRDT 式无冲突协同。

在我们的西安原型里，定制前台先访问本地适配服务，由适配服务调用 TREK 的旅行、地点、日期与安排接口，保存后重新读取数据验证。我们确实复用了这一条业务链；精选内容、推荐排序和插画交互是另外编写的。

### 地点搜索、地图、路线与导航各有职责

| 层次 | 固定版本中的实现与依赖 | 不应混淆的事情 |
| --- | --- | --- |
| 地点数据 | TREK Places API 使用 Overture 数据索引，并与 OSM 搜索整合；Google／高德可作为配置后的补充或回退 | TREK 有自己的地点服务整合与索引能力，但基础地理资料并非全部自己采集 |
| 周边分类探索 | 优先使用 TREK Places，必要时回退 Overpass 等 OSM 服务 | “附近有餐厅”不等于“这家适合你、值得推荐” |
| 地图渲染 | 按配置接入 Leaflet、MapLibre、Mapbox 等前端地图能力与底图 | 渲染地图不自动产生可信票价、开放时间或景点推荐理由 |
| 地点顺序 | 最近邻＋2-opt 等基于坐标距离的启发式优化 | 主要解决排列顺序，不保证全局最优，也不等于营业时间／预约时段约束排程 |
| 道路计算 | OSRM 等路线服务给出道路形状、距离和预计时间 | 不能当作实时交通承诺；路线失败状态和示意直线要区分 |
| 实际导航 | 将目的地交给外部地图服务 | 地点中心不一定是可进入门点，地图链接也不证明已实地完成导航 |

固定源码中的地点服务已核对至 `server/src/nest/maps/maps.service.ts`、`trek-places.client.ts` 和 `providers/amap.provider.ts`。因此不宜把该版本简单概括成“只有 Google 或 OSM 搜索”。

上游在部分道路查询失败场景中可以保留直线展示；我们的西安适配版要求明确显示失败，避免把直线或驾车结果冒充步行道路。这两个实现的行为应分别记录。

### 离线、AI 和 MCP

PWA / Workbox 与 IndexedDB / Dexie 等承担缓存和有限离线操作；地点、行李等对象可以有离线编辑路径，外部地图瓦片、路线、天气和实时数据不能因此视为始终可用。重连冲突行为需要另外测试。

预订解析与 AI 主要帮助从文件中提取信息；MCP 则让外部 AI 通过受权限限制的工具读写旅行。它们不是自动可靠的旅行推荐来源，也不代表自动预订成功。

进一步依据：[地点搜索](https://github.com/liketrek/TREK/blob/b98787f83698f3beee1b9a8475121c52f0caf07c/wiki/Places-and-Search.md)、[TREK Places](https://github.com/liketrek/TREK/blob/b98787f83698f3beee1b9a8475121c52f0caf07c/wiki/TREK-Places-API.md)、[路线优化](https://github.com/liketrek/TREK/blob/b98787f83698f3beee1b9a8475121c52f0caf07c/wiki/Route-Optimization.md)、[离线范围](https://github.com/liketrek/TREK/blob/b98787f83698f3beee1b9a8475121c52f0caf07c/wiki/Offline-Mode-and-PWA.md)、[MCP](https://github.com/liketrek/TREK/blob/b98787f83698f3beee1b9a8475121c52f0caf07c/wiki/MCP-Overview.md)。

## 3. 我们做了什么：成果与状态

| 阶段 | 实际成果 | 状态与边界 |
| --- | --- | --- |
| 原版实测 | 本机运行完整 TREK；验证地图地点联动、道路展示、行程、费用与清单，刷新后数据仍保存 | 已实测；人物、费用和预订是演示样本，没有真实交易。跨账号协作、离线冲突、AI/MCP、各类导出未全面实测 |
| 西安 V1 定制 | 13 个精选地点（9 景点、4 餐饮）、7 个图上热点和 6 个图外地点、11 张带来源照片；偏好与规则排序、三日安排、真实地图、道路查询、高德入口及保存 TREK | 已实现并冻结归档。精选内容和插画交互属于本项目；不是 TREK 自动生成。旧插画存在方位／文字问题，热点为手工关联 |
| D0 技术设计 | 定义真实地点、照片、地理骨架、景观素材、程序合成、地点关联和出行资料之间的关系 | 设计记录；同一地点编号串起不同视图 |
| E1 地理布局 | 选钟楼、鼓楼、大雁塔、兵马俑比较连续全域图与分区放大图；保存坐标、图幅、锚点和检查记录 | 四点布局验证完成。密集地标需要局部放大，全域定位解释实际关系；通过的是相对给定输入的计算一致性，不是实地精度认证 |
| E2 素材与放置 | 5 次内置图像生成得到 4 张当前素材和 1 张拒收图；保存真实参考、提示词、原图、身份、哈希及程序放置记录 | 候选。大雁塔六层错图被发现并修成七层；透明边缘、建筑细部、内容锚点、实际主体可见率与整体美术质量仍有未完成项 |
| E3 从图到行动 | 规划新导览图、真实地图、入口、费用、预约及资料更新之间的完整体验 | 未执行。V1 的导航入口和预约提醒不能视为新流程已验收 |

最大的三个研究收获：

- **位置正确与外形正确要分别审核。** 大雁塔六层错误不会被素材编号或位置检查发现。
- **一张图不宜承担所有比例。** 城区密集地标与远郊景区可以采用“全域定位＋局部放大”，明确不同图幅的比例。
- **画面、地点事实与行动信息分开维护。** 票价变动通常只需更新地点资料；素材或位置变化则触发图稿与关联检查。

## 4. 可扩展目标：若未来决定继续

主方向是**首次到陌生城市的可交互视觉导览**。以西安为例，游客主线为：

`看图理解片区 → 选景点与餐厅 → 看实拍、费用与预约 → 确认入口和路线 → 收藏或安排`

制作端主线为：

`可信地点与真实参考 → 地理布局 → 景观素材生成 → 受控合成 → 名称与热点 → 地点关联与资料维护`

同一个地点编号连接插画坐标、真实地图坐标、详情和行程。景区中心、建筑中心与实际入口分开记录；票种、价格、开放、预约和核实时间独立保存。图片是帮助理解与选择的入口，不能替代事实维护。

| 可选延伸 | 可以复用什么 | 继续前需验证什么 |
| --- | --- | --- |
| 更多城市的首次到访 | 地点模型、图幅规则、素材流程、地图与行程接口 | 各城资料质量、地标密度、制作与更新成本，不预设已能任意城市自动生成 |
| 景区、街区、园区导览 | 图像与真实地点关联、资料卡、路线衔接 | 门点、可通行范围、实际路径、分时开放信息 |
| 亲子、陪父母、轻体力路线 | 偏好、分日安排、收藏及解释规则 | 步行负担、设施和可达性来源，不能凭标签做无障碍承诺 |
| 本地生活与主题探索 | 地点选择、具体餐厅分店与图像入口 | 内容可信度、推荐理由、营业变化，不能以通用菜品照片代表门店出品 |
| AI 行程助手 | 受控 API / MCP 与已有旅行状态 | 授权范围、事实核验、用户确认及写入后验证 |

实时余票、交易支付、可靠营业状态、实时交通和高质量个性化推荐需要另外的数据或服务接入；当前没有这些完整交付。内容与图片来源、坐标系、资料核实日期及过期状态也需要随产品一并维护。

## 5. 对你的意义

**工程上：** 有可运行的旅行系统和数据承接方式，后续不必同时从零搭建账号权限、旅行、每日安排、费用与持久化。也可以只学习其领域模型，是否复用整套代码应在产品目标明确后决定。

**产品上：** 可以把主要精力放在帮助用户认识城市、选择值得去的地方，并获得可信行动信息。真正需要验证的是用户是否选得更快、理解得更清楚、出发时少走弯路。

**研究上：** 原版实测、V1 归档、地点数据、参考照片、生成素材、失败案例和检查方法已留下。即使暂不继续实现，这些资料仍能用于评估其他城市导览、地图内容和 AI 助手项目。

**投入上：** 已有实验提示，内容核实、图像审核和资料更新会占用持续工作量；不宜仅凭地图已接入或图片已生成就判断产品成本很低。下一次决策应围绕一个完整用户任务的价值，再决定继续投入。
