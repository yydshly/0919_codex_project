CHAPTER 03 / 建议先读

Prompt 工程

通过任务说明、背景、示例和输出约束，帮助模型理解你要什么。

放到实际工作中

让 AI 整理会议记录时，提供“决定 / 负责人 / 截止时间”的样例，并要求缺失项写“未提及”。

它改变了什么

改变当前输入和上下文；通常不更新模型参数，也不等于永久学会你的习惯。

适合：写作、提取信息、分类、规范输出格式。

三种方法，解决不同问题

Prompt把要求说清楚
RAG · 检索增强把相关资料找出来
微调用训练调整任务表现

A / 管理角色

群体可以变化

运行过程中增加或移除角色，调整身份和行为配置，用来表达人口与组织的变化。

B / 干预实验

条件可以改变

修改环境参数或插入事件，再观察角色之间的互动如何变化。

C / 复用结构

核心与场景分开

微内核处理调度、通信和行为校验；插件承载具体场景逻辑，便于在不同实验中复用。

PRODUCT DIRECTIONS / 我们的理解

多角色交互，怎样变成有用的产品？

让角色拥有不同信息、目标和资源，在互动中相互影响。产品价值来自可演练、可比较、可复盘的过程；以下是需要进一步开发和验证的方向。

六种多角色产品方向及输出
产品方向角色怎样互动用户得到什么
沟通陪练
建议优先验证		真人与客户、采购、主管等 AI 角色沟通，发现诉求并处理分歧。情境练习、对话回放、遗漏分析和有证据的改进建议。需要行业案例和评分标准。
AI 助手测试台
建议优先验证		虚拟用户提出请求，订单、库存、审批等角色或程序按规则响应。失败案例、规则违反记录和版本对比。用业务状态与标准答案检查结果。
服务流程沙盘顾客、员工、主管和供应商共同完成服务流程。观察排队、交接冲突和资源瓶颈。需要实际业务数据校准。
协作与应急演练各角色持有不同信息与职责，共同应对变化的事件。信息遗漏、响应延误与复盘报告。情境和规则需要领域专家参与。
游戏 NPC 与剧情有目标、关系和记忆的角色彼此互动，并回应玩家。动态事件、人物关系和可变化剧情。重点控制一致性、延迟与成本。
方案与传播推演模拟使用者、购买决策者、客服等角色，探索可能的疑问与冲突。待验证的假设与潜在误解。不能替代真实用户研究或预测市场反应。
选择标准

互动真实有必要，结果能够验证

角色之间是否真的互相影响？结果能否通过规则、任务结果或真人表现验证？用户是否有反复培训、测试或演练的需求？

从小场景开始

明确规则交给程序，复杂交流交给 AI

时间、库存、排队和权限由程序处理；模型参与语言、偏好与协商。先验证一个有明确目标的场景，再扩展规模。

以上为产品研究判断，尚未验证业务效果与付费意愿。阅读完整产品方向与验证思路。
