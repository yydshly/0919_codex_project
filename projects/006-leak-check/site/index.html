Leak Check / 研究摘要

已有数据关联查询，
邮箱账号盘点的探索。

能力与原理
在已有 SQLite 数据中精确匹配邮箱、手机号等标识，提取共同标识继续查表，默认两轮后聚合脱敏。
数据边界
没有实时全网搜索，也不提供作者真实数据。仅凭电话或邮箱查全注册平台，现有方案无法兑现。
我们的探索
独立开发「拾迹」原型：用户授权后自动分析历史邮件，整理平台注册与使用证据，供本人核对。
对我们的意义
原库可供参考，直接复用有限；保留邮件整理方向，评估能否帮助找回遗忘平台、减少翻信，真实效果仍待验证。

DISCUSSION NOTES / 我们已确认的理解

先明确数据从哪里来，再判断产品能做什么。

后续接入暂缓
01 / 原库的本质

在已有数据里找关联

按邮箱、电话等标识匹配记录，再提取共同标识继续查询。核心是数据库检索与程序里的分轮关联，不是实时搜索整个互联网。

02 / 对我们的价值

可参考实现，关键仍是数据

关联和脱敏代码有学习与原型价值。它不提供真实数据获取能力，对“输入邮箱就找到全部注册平台”的原始目标，直接帮助有限。

03 / 可以继续的方向

从自己的邮件找回账号足迹

经用户授权，分析历史邮件中的注册和使用证据。这是独立开发的产品方向，不是原库自带能力，也不能补全没有留下邮件的账号。

当前决定

保留源码研究和现有「拾迹」原型，先归档理解与边界。邮箱适配、真实账号验证和后续功能，待恢复开发后再推进。

PRODUCT DIRECTION / 面向个人用户

「拾迹」：有邮件证据的账号盘点。

帮助用户找回遗忘的平台，核对账号足迹。
产品价值仍需真实使用验证。

原始设想 · 现有方案无法兑现

一个手机号或邮箱，查遍所有注册平台

各平台的内部账号数据不会因知道邮箱地址而对外开放。公开网页只能提供公开线索，已知泄露库只能覆盖已收录数据，两者都不是完整注册名录。

保留方向 · 用户授权后分析

从历史邮件中找出注册与使用线索

主流程是连接自己的邮箱、完成授权、自动读取和分析。文件导入作为备用方式。输出平台、证据和相关时间，再由用户核对归属。

  1. 01连接邮箱输入地址，识别服务商
  2. 02用户授权官方登录或客户端授权码
  3. 03自动读取显示实际读取范围
  4. 04整理证据解析邮件、归组平台
  5. 05核对与导出确认使用过或排除误判

每种邮件，能证明的事情不同。

最早相关邮件不是注册日期；历史使用记录也不能证明账号今天仍然存在。邮箱验证身份与读取邮箱内容是两种不同的授权。

注册成功 / 账号创建
较明确的历史注册线索，仍需核对是否属于本人。
登录 / 订阅状态
可以支持曾使用平台的判断，不自动认定注册时间。
验证码 / 重置请求
只能说明出现了操作请求，不代表操作完成。
推广 / 普通购买收据
不能单独认定注册，可能是营销投递或访客购买。
价值如何判断？

不能只看识别出多少个平台。后续应验证：是否帮用户找回遗忘账号、证据是否可信、误报是否容易纠正，以及整理账号是否节省时间。订阅整理和注销引导列为后续探索，暂不承诺自动注销。

05 / PRACTICAL LIMITS

落地之前，要看见这些边界。

以下来自固定版本的代码审查。
邮箱清洗问题已用虚构输入复现。

!

关联线索，
不等于身份结论。

手机号换主、共享邮箱或错误数据，都可能把不同人的记录连在一起。当前没有归属校验或关联置信度。

阅读完整源码分析 ↗
邮箱中的连字符会被误删01

例如 alice-test@example.com 会被清洗为 alicetest@example.com，可能查错或漏查。应按输入类型分别处理字符。

“最多 64 条”并不是严格上限02

代码先读取一轮的全部匹配记录，再检查是否达到 64 条。因此单轮可能超过上限；12 条阈值只触发日志告警。

示例库没有准备查询索引03

已检查示例库：手机号、邮箱、身份证号和 QQ 均未建立查询索引。实际部署需自行配置；不能由此推断作者线上是否有索引。

输出脱敏不等于全程不留痕04

异常命中过多时会打印完整查询标识。接口里也没有鉴权和限流实现，不能只凭“不记录查询”的宣言评估实际行为。

结果数量和来源需要谨慎解读05

数据量接口使用最大 rowid，而非真实计数。各字段先打码后去重，不同原始值可能合并；来源列表不保留逐条对应关系。
