TECHNICAL BRIEF SHADOWROCKET-ADBLOCK-RULES-FOREVER

用一份配置，说明
请求该怎么处理。

这个库把广告名单、代理黑名单与直连白名单整理成 Shadowrocket 的 .conf 配置。客户端加载后，按目标域名或 IP 决定直连、走代理，或拒绝请求。它的主要价值是持续整理名单，减少手工维护。

交付物：.conf 规则文件执行端：Shadowrocket代理出口：需自行提供
01 / ROUTING

用黑白名单分流

代理黑名单通常命中走代理；直连白名单通常命中直连。未命中的请求按所选配置的默认策略处理。

决定 DIRECT 或 PROXY
02 / BLOCKING

用广告名单拦截

广告域名或 IP 命中拒绝规则时，由 Shadowrocket 阻止请求；它与“代理黑名单”是两种不同用途的名单。

决定 REJECT
03 / MAINTENANCE

生成并更新配置

脚本汇总上游名单、去重并合并人工例外，再按模板生成不同模式的配置；客户端需自行更新并启用。

降低规则维护成本
先分清三件事

规则决定怎么走，客户端负责执行，节点提供出口。 单独下载这个仓库不会获得代理服务，也不会自动改变设备上的网络设置。

已经在用另一份配置，还能使用这个库吗？

两份完整配置可以保留并切换，但不会自动把规则叠加。若已有分流设置，只想补广告过滤，可以把“仅广告规则”按客户端支持的方式合入现有配置；同一目标命中多条规则时，要核对匹配顺序和例外。节点订阅提供出口，规则配置决定何时使用该出口。

广告规则并非完整移植

ad.py 从 EasyList、EasyList China、乘风和 Peter Lowe 等源中提取整域拦截项；跳过含 ## 的元素隐藏规则和含 $ 的条件规则，也排除部分复杂 URL 模式。

更新是两件事

仓库生成新配置后，设备仍需下载、更新并启用。README 写的是每日北京时间 8:00；所核对构建工作流的定时表达式为 0 23 * * *，按 UTC 换算是北京时间 7:00，且实际调度可能延迟。应以工作流与文件时间为准。

05

能拦截请求，不等于能移除所有广告

效果取决于广告如何分发、名单是否覆盖，以及是否与正常内容共用地址。

较适合

独立广告域名

正文来自业务域名，广告来自单独域名。拦截广告请求后，正文仍可能正常加载。

难以区分

广告与内容同源

同一个域名同时分发正文和广告。整域拒绝可能一起阻断正常内容，产生误拦截。

不保证有效

视频流与页面布局

不能保证清除 YouTube 或其他视频广告；不负责删除网页广告容器，可能留下空白。

HTTPS 解密：基础域名拦截是否需要证书？

域名 / IP 级拒绝规则本身不要求读取 HTTPS 正文。仓库还包含 URL Rewrite 与 MITM 配置，例如 google.cn 跳转；这属于另一层功能。HTTPS 重写需要客户端具备相应解密条件，不能把导入规则等同于必须启用 HTTPS 解密。

模板中的 MITM 主机名包含 *.googlevideo.com，仅凭这一项也不能推断已经实现完整 YouTube 去广告。

速度、隐私与实时性：哪些结论不能直接推出？

减少无用请求或不必要的代理绕路，可能改善体验；实际速度仍由网络、DNS、节点与服务端共同决定。阻断部分跟踪域名不等于匿名。仓库自动重建不等于每一条上游名单都更新及时，也不等于每一条规则都经过真机验证。

README 对匹配树与缓存的说明是作者描述；本研究未审计 Shadowrocket 引擎，不将其“O(1)”说法视为所有规则类型的严格复杂度证明。

06

对你最有价值的是：少维护，少切换

先判断自己是否使用 Shadowrocket，再决定需要分流还是仅广告过滤。

A

已经使用小火箭

可作为基础配置起点。先保留现有配置，选择符合需求的模式，再检查常用网站和 App；出现异常时结合日志定位误拦截或分流问题。

直接适用
B

只想减少手机广告

关注“全局直连 + 去广告”。该模式不依赖代理节点，但需要客户端执行规则；对视频、信息流和同域广告保持合理预期。

部分适用
C

主要在 Windows 上工作

先确认实际客户端支持的配置格式。这个研究网页可以直接阅读，但 Shadowrocket 配置不能被当成通用的 Windows 网络设置。

需适配客户端
