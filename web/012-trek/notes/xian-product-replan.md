## 1. 已确认的产品定位

基于真实地理数据和景观资料，生成可探索的城市导览图，帮助第一次到访的人认识城市、发现值得去的地方，并获得费用、预约、位置和到达指引。

面向用户的表达：**第一次来这座城，从一张图开始：看哪里值得去、了解怎么玩、知道怎么到。**

图片生成是产品的生产能力；用户使用的是可以点击、了解和行动的城市导览。两者共用可信的地点库、固定地点编号和可追溯的来源。西安继续作为首个样本城市，重点验证首次到访者的景点与地方美食探索。

已确认的优先级：

1. 真实地理位置和景观参考在生成前进入约束，贯穿整个生成过程。
2. 图上的景观与真实地点一一关联，图片与地图可以互相定位。
3. 点击地点后能获得实际出行指引，包括票务、预约、入口和交通。
4. 收藏、地点串联、行程保存承接上述体验；现有三日行程是复用基础，不再规定所有用户都必须先生成三日计划。

## 2. 用户体验与生产流程

| 视角 | 主流程 | 成功结果 |
| --- | --- | --- |
| 游客 | 看图认识片区 → 点开感兴趣的地点 → 看实拍与游览信息 → 核实费用与预约 → 查看真实位置和到达方式 → 收藏或安排 | 能说清为什么去、需要准备什么、去哪里进入 |
| 内容与生成维护 | 收集地点 → 核实坐标和外观 → 确定地理骨架 → 生成景观素材 → 受控合成 → 添加标签与热点 → 检查 → 发布对应版本 | 能追溯每个地点的位置、素材、资料和输出版本，能够局部更新 |

游客页面优先展示地点信息和行动入口；生成参数、坐标转换、位置检查报告等保留在维护与研究界面。

## 3. 真实数据驱动的生成链路

### 3.1 地点数据

每个景点、餐厅分店、交通参照点有稳定编号。保存正式名称、别名、类型、所属片区、坐标系、地理坐标、具体来源与核实日期。餐厅记录到具体分店；同名景区、不同馆区分别建立记录。

景区范围中心、建筑位置与可进入的门点分别保存。当前原型中的一部分坐标是范围中心，并非入口；不能直接继承为已核实的导航入口。

### 3.2 地理骨架

根据坐标与范围确定片区、东西南北关系、河流道路参照和主图覆盖范围。保存使用的投影或布局规则、原始地理锚点、允许的视觉偏移及坐标转换过程。

先比较两个候选方案：一张连续的城市景观图，以及主图搭配明确标注的城区放大图／远郊分图。密集区可以放大，跨图幅不比较像素距离；空间压缩需标明并接受位置关系检查。艺术化表达不承担导航测距。

### 3.3 景观素材生成

使用已核实的实拍、建筑外形资料与授权参考生成单个或小组地标素材。保存参考来源、生成模型、实际提示词、时间、素材编号、图像尺寸、内容哈希和允许使用范围。

AI 主要负责建筑与景观的视觉表现。地标外形需要独立检查；“素材编号正确”不能证明“建筑画对”。未核实素材保持待确认状态。

### 3.4 受控合成

程序将素材放入地理骨架指定区域，记录实际变换、素材身份和图像输出，检查错位、漏画、重复、越界与重要地标遮挡。背景、树木与地面衔接服务于整体画面，但不能抹去地理约束证据。

若对整图进行后续生成或润色，需要重新校验实际输出，不能沿用润色前的合成通过报告。

### 3.5 程序标签与热点

名称、图例、方向提示、片区范围和点击区域由程序叠加。保存画面位置与热点形状，并通过地点编号关联真实地理位置。名称和交互信息可维护，不依赖模型在图片中正确绘制文字。

### 3.6 真实地图与出行引导

插画与真实地图共享地点编号，分别保留画面位置和真实坐标。点击任一视图后，详情与另一视图同步到同一地点；出行路线与导航依据真实坐标和正确入口。

票价、开放时间等变化信息作为关联资料更新，通常无需重绘底图；名称、地点迁移或重要景观外形变化则触发受影响内容的重新生成与验收。

## 4. 地点资料应包含什么

| 数据组 | 最小内容 | 展示与更新规则 |
| --- | --- | --- |
| 身份与位置 | 稳定编号、正式名称、馆区／分店、地址、坐标与坐标系、范围中心、入口 | 明确入口是否已核实；不能用品牌名替代具体门店 |
| 景观依据 | 实拍与建筑资料、作者、来源、许可、核实日期 | 区分景点实拍、菜品参考与生成插画 |
| 游览信息 | 看点、适合人群、估计停留、步行负担、已核实的设施 | 估计与事实分别标注，不伪装成实时状况 |
| 票务 | 票种、适用人群、票价与币种、包含范围、有效期、优惠条件、官方入口 | 单票、联票与收费展分别记录；免费入园与收费项目区分 |
| 开放与预约 | 常规开放时段、闭馆日、预约要求、官方预约入口、临时公告 | 显示来源、核实日期及有效期；加入安排不表示预约成功 |
| 到达 | 已核实入口、交通方式、真实地图入口、路线服务结果 | 时间为估计；服务失败明确提示，不能以直线代替道路 |
| 更新状态 | 来源链接、采集／核实时间、有效期、冲突与待确认状态 | 过期或冲突信息降级为待确认，提示前往官方渠道核实 |

票务首阶段提供核实后的信息和官方跳转，不实施购票、支付或预订。实时余票、营业状态、实时交通需另行接入可靠服务，并单独验收。

## 6. 旧「城景工坊」可复用的研究与边界

旧项目位置：`F:/codex_project/0913_codex_project/projects/009-city-landmark-map/`。

已读研究记录：`scenic-material-integration.md`、`automatic-position-audit.md`、`README.md`。

旧项目曾生成 8 处景区的透明素材，完成受控合成与自动位置检查；保存了素材身份、哈希、实际像素与输出报告。故障实验可以检出位置互换、遗漏、遮挡和编号串用。其城区独立放大方案值得继续比较。

其“8/8 位置通过”仅证明：绑定素材按给定约束参与了实际合成，未发现该套检查可检测的错位、漏画等问题。它没有证明输入坐标一定正确、每张素材外形真实、任意外部整图都能自动识别景区，或最终作品已经达到交付质量。旧报告中的作品状态仍为 pending，景观真实性仍为 unverified。

旧实验使用 GCJ-02，当前地图主要使用 WGS84。复用前要确定统一数据约定及转换边界，禁止混用；不能以程序内部一致代替地理来源核实。半透明遮挡、复杂景区轮廓、素材拼贴感和主城区密度仍需继续研究。

原西安 V2 用户上传图继续作为视觉参考与历史成果保存；不能把它重记为本次新生成图，也不能据本地复用推断已获得公开或商业发布许可。

## 7. 分阶段里程碑与验收门槛

各阶段先评审上一阶段证据再推进；以下为下一阶段计划，不表示已经实现。

| 阶段 | 产出 | 验收门槛 |
| --- | --- | --- |
| M0 保存研究基线（本次） | 原型源码与资料、截图、运行说明、能力清单、备份与校验记录、新规划 | 能定位原版本并说明如何恢复；备份清单与实际文件一致；现有界面不被规划改写 |
| M1 可信地点模型 | 西安试点地点集、坐标及入口记录、实拍参考、票务与开放结构 | 所有发布条目有编号、来源、核实时间与坐标系；试点入口可逐项核实；未知信息显式保留 |
| M2 地理约束生成实验 | 地理骨架、布局方案比较、素材、合成图、标签热点、检查报告 | 每个图上地点有生成追溯；错位／漏画等故障能被拦截；方位、外形与审美分别验收，位置通过不代替其他质量判断 |
| M3 一图到出行闭环 | 图与地图联动、游览详情、票务与预约跳转、入口导航、收藏 | 从图选一个地点能查费用与预约、确认入口并打开匹配地图；过期资料和接口失败都有清楚状态 |
| M4 用户与复用验证 | 首访用户任务记录、第二城小样、生成维护成本记录 | 用户能解释片区与地点关系并完成出行准备；第二城沿用同一数据与生成流程，明确实际人工工作量 |

建议 M2 先选少量、形态差异明显且资料充分的地标，避免在质量未稳定时直接扩展全城。具体数量、画幅和成本目标在 M1 后根据密度与资料质量确定。

## 8. 后续分析需要回答的问题

1. 用户最需要城市全景、片区图还是抵达点周边图？以什么边界覆盖“第一次来”的核心需求？
2. 哪种布局既保持方位可信，又能让密集城区地标可辨认？连续图与分幅方案如何取舍？
3. 地点坐标、入口、道路、实拍与票务分别采用哪些来源？遇到冲突如何判定和记录？
4. 地标外形检查能自动完成到什么程度，哪些需要人工内容审核？怎样避免把位置校验冒称真实性审核？
5. 图像风格能否统一，背景衔接能否自然，并保留完整生成与校验证据？
6. 一个城市的初次制作、一次地点变更和一次票价更新分别需要多少时间与成本？
7. 当前 TREK 接口在收藏、行程与长期维护中承担什么角色？哪些信息应由本产品单独管理？
8. 数据和图片的可用范围是否支持计划中的发布方式？公开发布前还缺哪些来源或授权证据？
9. 用户能否更快理解城市并完成“选地点—了解费用—确认预约—找到入口”，相较图文清单改善在哪里？
