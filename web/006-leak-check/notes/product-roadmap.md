## 我们最初想解决什么

最初目标是：个人用户输入自己的手机号或邮箱，就能知道曾在哪些平台注册、哪些信息发生过泄露。

仅凭一个标识，无法可靠、完整地得到这份清单。平台内部的账号表通常不对外开放；没有发现公开记录，也不代表没有注册或没有泄露。必须先回答“能够合法访问哪些数据”，再决定可以给用户什么结果。

| 数据来自哪里 | 可以提供什么证据 | 不能据此推断什么 |
| --- | --- | --- |
| 可访问的公开网页 | 某个标识出现在某个页面，并保留来源和检查时间 | 不能读取网站内部账号表；公开出现不自动等于泄露 |
| 已接入的已知泄露数据源 | 在该数据源的覆盖范围内发现相关记录或事件 | 不代表完整注册清单；没有命中不代表安全 |
| 用户授权读取的私人邮箱 | 欢迎邮件、注册成功通知、登录提醒等历史线索 | 邮件可能缺失；历史线索不证明账号现在仍存在 |

## Leak Check 实际解决了哪一部分

固定版本源码实现的是：输入标识 → 查询已有 SQLite 数据 → 提取命中记录里的其他标识 → 默认再查询一轮 → 合并并脱敏输出。查询采用字段精确匹配，关联主要是应用程序围绕同一张个人信息表重复查询；来源表用于解释数据来源。

它没有提供互联网实时搜索、平台内部数据访问、作者数据同步或历史邮件分析。关联价值取决于事先导入的数据：不同记录共享邮箱或电话时，可以找到更多相关记录；共享标识本身不能证明所有记录属于同一个人。

因此，对我们的原始产品，主要缺口是数据来源和覆盖范围，这个库没有补上。描述中“互联网传播的数据”容易被理解为“实时在互联网查找”，更准确的解释是查询已经收录的数据；现有证据不足以判断作者有意误导。作者托管服务和自行部署源码也不能混为一谈。

## 保留下来的产品方向：邮件驱动的账号盘点

「拾迹」面向个人用户，帮助整理邮件中留下的平台注册或使用痕迹。交付是**平台名称、线索类型、相关邮件和时间、用户确认状态**，不是“全部注册账号”或“当前仍有效的账号清单”。

这是独立开发的产品方向，改变了最初“只输入电话或邮箱就能识别”的条件。Leak Check 的数据库检索代码没有直接用于现有原型，直接复用价值有限。

预期使用流程：

1. 输入自己的邮箱，选择邮箱服务商。
2. 完成邮箱服务商要求的授权。输入地址或证明能接收验证码，不等于授权读取历史邮件。
3. 自动读取用户同意范围内的邮件；文件导入仅作为备用方式。
4. 将各服务商邮件转换为统一格式，再解析、分类、去重和聚合。
5. 按平台展示证据，允许用户确认、排除误判和导出清单。

| 分类 | 例子 | 展示含义 |
| --- | --- | --- |
| 注册线索 | 明确的账号创建成功通知 | 有历史注册证据，仍需核对归属 |
| 使用记录 | 登录提醒、订阅状态通知 | 有使用线索，不自动认定注册时间 |
| 验证请求 | 注册验证码、密码重置请求 | 有请求发生，不证明注册完成或请求由本人发起 |

普通营销邮件和订单不能单独证明注册。最早一封相关邮件不是准确注册日期，平台数量也不等于账号数量。发件地址可能被伪造，平台映射不能当作身份认证。

| 项目 | 当前状态 |
| --- | --- |
| 示例、`.eml` / `.mbox` 导入、邮件分类、平台聚合、证据展示、人工确认和 CSV 导出 | 已有本地原型；20 项解析与分类测试及浏览器交互验证通过 |
| QQ / Foxmail、163 / 126 / Yeah 自动读取 | 已有固定服务商的本机 IMAP 连接代码；21 项后端离线测试和模拟连接流程通过 |
| 实际读取范围 | 当前设计为收件箱最近 100–3,000 封，受单封与总量限制；不覆盖所有文件夹 |
| 网络检查 | QQ、163 的加密连接曾验证可达；这不等于成功登录用户邮箱 |
| 真实邮箱读取与识别效果 | 尚未完成真实账号授权验证；没有真实邮件准确率或召回率数据 |
| Gmail / Google Workspace、Outlook / Hotmail | 尚未接入；列入恢复开发后的适配计划 |

本机自动读取需要运行本地服务，普通静态网页只具备示例和文件导入能力。当前实现不将授权码与邮件正文写入磁盘，使用临时内存处理；这不等于已经具备面向公众的完整运营能力。详细限制见[原型记录](mail-trail.md)。

## 为什么不同邮箱需要适配

共用的是邮件解析、证据分类、平台聚合和展示；需要适配的是登录授权、邮件读取接口、文件夹或标签、分页、限额和失效处理。

| 邮箱 | 后续接入方式与边界 |
| --- | --- |
| QQ / Foxmail、网易个人邮箱 | 保留现有客户端授权码与 IMAP 实现；恢复开发后验证真实账号兼容性和错误提示 |
| Gmail / Google Workspace | 优先规划 Google OAuth 与 Gmail API，只申请所需只读访问；需应用配置、授权回调、令牌管理和撤销处理 |
| Outlook / Hotmail | 后续规划 Microsoft 委托授权与 Graph 邮件读取，复用统一分析模块 |
| 其他邮箱、企业邮箱 | 在具体需求出现后评估；组织管理员策略和服务器差异需要单独验证 |

Gmail 本身支持 IMAP；符合账号条件、开启两步验证的用户也可能使用应用专用密码。因此 Gmail 当前未支持，是接入尚未实现，不是技术上无法读取，也不是只能用 OAuth。面向个人用户的产品仍优先考虑服务商授权页面，减少用户手动配置。

Google 的 `gmail.readonly` 属于受限权限，正式面向公众上线需要评估相应验证要求；工作区或企业账号也可能受到管理员策略限制。相关配置和验证均未完成。

## 后期规划：以验证结果决定下一步

| 阶段 | 要做的事 | 进入下一步前需要的证据 |
| --- | --- | --- |
| 0 · 当前暂停 | 整理结论、能力边界、现状与待办；保留已有原型 | 文案能明确区分已实现、模拟通过、真实未验证和后续计划 |
| 1 · 验证最小真实流程 | 恢复开发后，选择一种邮箱，由用户授权读取最近 100 封；检查连接、只读行为、证据和归属 | 真实读取成功，人工核对结果；能解释漏识别、误判和范围限制 |
| 2 · 扩展邮箱接入 | 优先 Gmail，再按需求接入 Outlook；处理取消授权、令牌过期、撤销、限额和读取失败 | 各服务商分别通过真实授权与异常流程验证，共用结果格式 |
| 3 · 完善盘点覆盖与质量 | 多文件夹或标签、增量读取、多账号分离；建立经用户确认的评测样本 | 按线索类型衡量准确率和召回率，避免把增加读取量当作识别更准确 |
| 4 · 验证整理后的实际价值 | 评估遗忘订阅提示、不再使用的平台整理、注销指引与进度记录 | 用户能完成具体整理任务，并认可节省的时间；有价值再扩大投入 |

当前不继续申请凭据、不新增邮箱接入，也不把任何阶段表述为已承诺的上线日期。已有 QQ / 网易代码保留，真实兼容性验证和新增适配都留待恢复开发。

如果最终只得到一个平台列表，独立产品的价值仍需验证。订阅线索不等于仍在扣费；注销指引也不保证账号或平台保留的数据已经删除。后续应证明用户能完成具体任务，再考虑持续监测、云端服务或商业化。
