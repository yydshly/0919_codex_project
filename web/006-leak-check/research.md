# 006 · Leak Check：数据关联原理与邮件账号盘点探索

**针对已有个人信息数据库的查询后端：接收手机号、邮箱、身份证号或 QQ，精确匹配记录，扩展查找关联信息，再脱敏返回。**

原理是按字段查询已有 SQLite 数据，从命中记录提取共同电话、邮箱等标识，再重复查询，默认两轮后聚合脱敏；主要是程序围绕同一张个人信息表展开检索。它不实时搜索互联网、不访问各平台内部账号表，也不附带作者的真实数据。

我们的探索从“输入手机号或邮箱就找到全部注册平台与泄露情况”开始，源码分析后确认核心瓶颈是数据来源与覆盖范围。最终保留「拾迹」这一独立原型方向：用户授权后自动分析历史邮件，提供可核对的注册与使用线索，而非完整账号清单。

对你而言，原库有查询、关联和脱敏的学习参考价值，但对原始产品目标的直接帮助有限；后续更值得验证的是邮件盘点能否减少翻信、找回遗忘平台、支持账号整理。现有原型尚未经过真实邮箱验证，新增适配继续暂缓。

## 当前理解与后续规划

**2026-09-22 决定：保留现有研究与原型，暂停进一步接入开发和真实邮箱验证。**

原始目标“输入手机号或邮箱，识别全部注册平台”不能由这个仓库兑现。库的直接价值在已有数据检索与关联实现，缺少的核心仍是数据来源。保留的产品方向为：用户授权读取自己的历史邮件，整理可核对的注册与使用线索；它与原库是独立能力，不能承诺完整账号清单。

研究网页已加入讨论结论、产品流程、证据边界、邮箱适配矩阵和分阶段规划。完整内容见[理解汇总与产品后续规划](notes/product-roadmap.md)。

QQ/Foxmail 与网易连接代码保留，真实授权和兼容性待后续验证；Gmail/Outlook 尚未接入，列入恢复开发后的规划。授权和收信按服务商适配，邮件分析与证据展示复用。Gmail 本身支持 IMAP，符合条件的账号也能使用应用专用密码，并非技术上无法支持。

后续顺序：单一邮箱真实验证 → Gmail/Outlook 授权适配 → 覆盖与识别质量 → 根据用户反馈评估账号整理价值。没有承诺上线日期，当前不继续实现这些适配。

## 网页能力展示

### 新增产品原型：拾迹 · 邮箱账号盘点

**输入自己的邮箱并授权后，自动读取历史邮件，整理平台线索清单及可核对证据。** 这是本研究延伸开发的独立产品能力，不是上游 Leak Check 自带功能，不依赖它的数据库。

- [在线原型入口](https://yydshly.github.io/0919_codex_project/006-leak-check/mail-trail/)：可体验虚构示例与本地文件分析。自动读取需运行本机版本 `http://127.0.0.1:5196/006-leak-check/mail-trail/`；[页面源码](mail-trail/index.html)。
- 主流程为“邮箱地址 → 邮箱客户端授权码 → 自动读取 → 平台线索”；本机连接服务实现 QQ/Foxmail、163、126、Yeah 邮箱的 IMAP 读取。
- 当前读取收件箱最近 100 / 500 / 1,000 / 3,000 封，不包含其他文件夹；超过 2 MB 的单封邮件会跳过，每次读取预算 25 MB，界面说明实际覆盖范围。
- 文件导入保留为备用入口，支持 `.eml` 和 `.mbox`；每批最多 25 MB、200 个文件、3,000 封邮件。
- 区分注册线索、使用记录和仅验证请求；按发件域名归组，去重后展示邮件主题、来源、时间、识别理由和正文摘录。
- 用户可以搜索、筛选、确认使用过、标记与自己无关，并导出包含证据概要与确认状态的 CSV。
- 虚构示例走相同解析流程：15 封导入邮件，合并 1 封重复，得到 8 个平台（5 注册 / 2 使用 / 1 验证），3 封未形成线索。
- 由仅监听本机的 Python 服务连接邮箱，邮件交给当前浏览器分析。授权码和原文不写入磁盘；完成后断开邮箱并清除服务端原文。刷新清空页面结果，每次盘点替换当前结果，分批请分别导出。
- 完整体验需运行 `python projects/006-leak-check/runtime/mail_service.py`（默认 5196 端口）；普通静态服务器仅支持示例与文件导入。
- 解析、模拟邮箱连接及浏览器流程测试通过；尚未用真实邮箱授权实测。Gmail/Outlook OAuth 未配置，暂不可连接。公网仅发布静态原型，未开放邮箱连接服务。

实现范围、边界和验证方式见[产品原型说明](notes/mail-trail.md)。原库能力研究页仍保留，导航中已增加产品入口。

## 源码实际具备的能力

| 能力 | 实现与结果 | 边界 |
| --- | --- | --- |
| 输入识别 | Pydantic 校验 `q`，正则识别手机号、邮箱、身份证号、QQ | 格式校验，不验证号码归属或身份证校验位；传入的 `type` 会被重新识别覆盖 |
| 精确匹配 | 对四类标识分别执行数据库 `IN` 查询 | 无模糊搜索、搜索引擎调用或在线网页检索 |
| 关联扩展 | 从命中记录提取其他标识，继续查询，默认最多两轮 | 不验证记录属于同一个人；默认不会遍历完整关系链 |
| 汇总展示 | 返回姓名、收件人、昵称、电话、邮箱、QQ、微博、地址、车辆、联系人、公司等字段 | 这些是返回字段，不代表支持按姓名、地址、微博号查询 |
| 脱敏 | 按字段保留部分字符，其他字符替换为星号 | 发生在响应阶段；数据库与查询仍使用完整标识 |
| 去重与来源 | 各字段脱敏后分别去重，来源名称原样去重返回 | 不保留每条记录和来源的一一对应；结果顺序没有保证 |
| 数据量展示 | 单独接口返回最大 `rowid` | 删除或跳号后不等于记录总数；空库返回字符串 `None` |

入口与输出见 [main.py](https://github.com/garinasset/leak-check/blob/7e3a113b9cf616b142ad5236c547c2c9a9246607/main.py)，校验见 [models/request.py](https://github.com/garinasset/leak-check/blob/7e3a113b9cf616b142ad5236c547c2c9a9246607/models/request.py)，脱敏见 [lib/masking.py](https://github.com/garinasset/leak-check/blob/7e3a113b9cf616b142ad5236c547c2c9a9246607/lib/masking.py)。

## 一次查询怎样执行

```text
请求：POST /dig/masking，主体为 {"q": "alice@example.com"}
  ↓
models/request.py：清理格式、识别输入类型
  ↓
main.py：选择 email / phone / id / qq 分支
  ↓
db/crud.py：查询本地 db/leak-check.db
  ↓
从命中记录提取新的邮箱、手机号、身份证号、QQ
  ↓
第二轮查询，以数据库 rowid 合并去重
  ↓
lib/masking.py：各字段打码、去重
  ↓
返回字段数组及来源名称数组
```

上面是应用路由；`root_path="/leak-check"` 用于部署前缀信息，实际外部 URL 取决于代理配置，不应简单当成所有本地路由自带此前缀。

例如一条记录有“手机号 A + 邮箱 B”，另一条记录有“邮箱 B + QQ C”。查 A 时先得到第一条，再通过 B 找到第二条。程序用精确相等的标识建立关联，没有 AI 推断或独立的图数据库。手机号换主、共享邮箱或脏数据都可能导致错误归属；它没有给关联结果计算置信度。

默认 `max_depth=2`、`max_records=64`、`threshold=12`。64 是每轮处理后的停止阈值，不是严格的 SQL 读取上限或输出上限；12 只触发日志告警，不会拒绝异常关联。[核心查询源码](https://github.com/garinasset/leak-check/blob/7e3a113b9cf616b142ad5236c547c2c9a9246607/db/crud.py)

## 数据从哪里来

代码固定连接 `sqlite:///db/leak-check.db`。安装脚本执行 `cp ./example.db ./db/leak-check.db`，没有下载作者真实数据的步骤。

本次只读取示例库的结构与统计，确认：

- `person`：8 条记录，包含个人信息及 `source_id`。
- `source`：4 条记录，保存来源名称。
- 没有手机号、邮箱、身份证号、QQ 的查询索引。

仓库没有数据采集器、数据导入管理界面、定时同步任务或远程业务数据库接口。数据准备和持续维护需在仓库外完成。“需要自行准备数据”不等于手工逐条录入，可以另外编写导入程序；只是这部分没有随仓库提供。

README 说可以使用其他数据库，但当前连接地址与 PRAGMA 针对 SQLite 写死。依赖里出现 PostgreSQL 驱动、pandas、openpyxl，并不代表已经实现数据库自由切换或 Excel 导入。[安装脚本](https://github.com/garinasset/leak-check/blob/7e3a113b9cf616b142ad5236c547c2c9a9246607/install.sh) · [依赖声明](https://github.com/garinasset/leak-check/blob/7e3a113b9cf616b142ad5236c547c2c9a9246607/pyproject.toml)

## 对我们有什么意义

这里以当前会话明确的目标——理解项目、判断是否部署、评估复用价值——为依据。没有证据表明我们已持有可用的个人信息数据集，下列业务场景因此是条件性建议。

| 我们的目标 | 它提供的价值 | 仍缺少什么 | 建议 |
| --- | --- | --- | --- |
| 偶尔查看自己的信息是否出现在已收录数据中 | 作者网站提供在线入口 | 本次未核验查询效果、覆盖度或实际日志行为 | 在线服务与源码分开评估；不需要为此先部署源码 |
| 自建一个与作者网站覆盖面相同的服务 | 可复用部分后端逻辑 | 作者真实数据库、数据更新机制，以及前端和服务治理 | 仅下载代码无法达成；有数据方案后再评估投入 |
| 对已有且有权使用的数据做内部暴露核查 | 精确匹配、跨记录关联、脱敏接口可作为原型 | 导入、索引、归属核验、字段级来源、鉴权和性能验证 | 数据条件满足时值得做小范围验证 |
| 给自有工具增加关联查询能力 | 可借鉴分层扩展、记录去重、响应脱敏 | 根据自己的对象、数据模型和访问规则重做适配 | 优先借鉴设计，不直接把原程序当作通用组件接入 |
| 建立互联网泄漏监控或实时告警系统 | 可作为未来系统的查询末端参考 | 采集、合法数据接入、事件识别、更新、订阅和告警 | 该仓库没有实现主要监控流程 |

与当前研究集的内容发布、视频处理、个人笔记项目相比，它提供的是独立的信息检索案例。当前没有验证与这些项目的集成，也没有理由为已有工具直接引入个人信息数据库。

**当前建议：收录研究，暂不投入生产部署；有明确数据来源与核查需求时，再做受控原型。** 其价值是可读、可修改的查询实现；是否值得落地，主要取决于数据和实际需求，而不是项目热度。

## 部署工作量与采用前的修正

| 层级 | 工作量判断 | 具体工作 |
| --- | --- | --- |
| 用示例库体验接口 | 较低 | Python 3.14、依赖安装、示例库、启动 Uvicorn；本次未实际启动 |
| 内部原型 | 中等 | 准备并导入数据、创建索引、修正查询问题、加入访问控制；按需要制作页面 |
| 持续对外提供服务 | 明显高于演示 | 数据维护、访问控制、限流、日志治理、前端、备份及规模验证 |

关键修正项按实际影响列出：

1. **输入准确性**：邮箱不能沿用电话号码的去连字符规则；独立验证已复现查询值被改变。
2. **检索成本**：为实际查询列配置索引；对单次 SQL 和返回结果设置真实上限。SQLite 参数优化不等于已经验证大规模能力。
3. **结果解释性**：保留每条信息的来源和关联路径，避免让使用者误认所有关联结果必然属于同一人。
4. **访问与日志**：接口没有鉴权和限流，异常命中会打印查询标识；“不记录查询”不能仅依据宣言成立。
5. **数据量口径**：区分记录数、去重人数和最大 `rowid`，避免展示含义错误。

详细代码定位、证据等级与验证方法见[源码审查笔记](notes/source-audit.md)。本研究没有修改上游程序。
